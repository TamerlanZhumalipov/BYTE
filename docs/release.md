# BYTE: подготовка к первому выпуску

**Статус 28.10.2026: код подготовлен к проверке на сервере. Публичный выпуск ещё не выполнен.** Сервера и домена пока нет. Локально Docker отсутствует; реальная изоляция Python/C++ проверена на Linux в [GitHub Actions](https://github.com/TamerlanZhumalipov/BYTE/actions/runs/40723205708). До запуска учеников обязателен `verify_judge` на целевом Linux-сервере.

## Что понадобится

- Linux VPS с Python 3.12, nginx, TLS и Docker с cgroup v2 (у rootless Docker также должна работать делегация cgroup). Подтвердить фактическое размещение базы, резервных копий и журналов в Казахстане в соответствии с опубликованными условиями BYTE.
- Отдельный непривилегированный пользователь приложения. Gunicorn слушает только `127.0.0.1:8000`. Не выставлять его порт в интернет.
- Для judge предпочтителен rootless Docker. Доступ к обычному Docker socket даёт полномочия уровня root; не выдавать его посторонним пользователям и не монтировать в контейнеры решений. Не применять `--privileged`, host network или отключение seccomp. Для большого публичного контеста нужен отдельный узел/сервис проверки с очередью; текущий синхронный judge занимает веб-воркер.
- Размер сервера выбирается после проверки с ожидаемым числом участников: стартовая конфигурация Gunicorn — два sync-воркера, максимум два одновременных контейнера, до 512 MiB каждый. Это ограничение ресурсов, не обещание пропускной способности.

## Обновление окружения и базы

Django 5.2 не работает на прежнем Python 3.9. Сохраните старое окружение до успешного переключения; создайте новое на Python 3.12. Изменения этого PR не устанавливаются автоматически в работающий сайт.

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade 'pip>=26.2.2'
python -m pip install -r requirements.lock.txt
```

Скопируйте `deploy/production.env.example` в `.env`, замените домен/пути и задайте случайный `DJANGO_SECRET_KEY` длиной не менее 50 символов. Не отправляйте `.env` в Git. Окружение процесса имеет приоритет над файлом. `DJANGO_DEBUG=0` — значение по умолчанию. Отсутствующий/слабый ключ останавливает запуск.

Для **собственной локальной разработки** используется `.env.example` с `DJANGO_DEBUG=1`. Judge по умолчанию требует Docker даже локально. `BYTE_JUDGE_BACKEND=local` допускается только при DEBUG и только для своего доверенного кода. В production локальный backend запрещён.

Перед миграцией существующей базы остановите приём запросов и сделайте согласованную копию средствами SQLite или уже установленной командой бэкапа. Для новой версии доступна:

```bash
python manage.py backup_database --output /srv/byte-backups/before-release.sqlite3
python manage.py migrate
python manage.py collectstatic --noinput
python manage.py check --deploy
```

`0011_requestbucket` добавляет таблицу общих лимитов. Бэкап создаётся через SQLite backup API, проверяется `integrity_check`, получает права 0600 и не перезаписывает существующий файл. Каталог копий должен существовать и находиться вне репозитория/static; доступ — только оператору. Проверять восстановление на отдельной копии; никогда не восстанавливать поверх работающей базы.

Настройки HSTS первоначально действуют один час только для текущего хоста. `check --deploy` пока выдаёт W005/W021: включение всех поддоменов и preload сознательно отложено до выбора домена и проверки HTTPS. Других предупреждений на проверенной конфигурации нет. Не подавлять эти сообщения; после запуска TLS принять отдельное решение об HSTS.

## Изоляция контестов — обязательная проверка

```bash
docker build --pull -t byte-judge:local -f deploy/judge.Dockerfile .
python manage.py verify_judge
```

Образ не содержит кода сайта, базы или ключей. Для каждого этапа создаётся контейнер с `--network=none`, read-only root, `cap-drop=ALL`, `no-new-privileges`, UID/GID 65534, лимитами CPU, памяти, процессов, файлов и временного диска. Монтируется только случайный каталог исходника/бинарного файла; при запуске решения он read-only. Эталонные ответы не помещаются в контейнер: сравнение выполняет Django-процесс снаружи. Вывод собирается вне каталога, доступного контейнеру, с мониторингом размера. По тайм-ауту удаляется контейнер, а не только Docker CLI.

`verify_judge` реально проверяет Python, C++, отсутствие доступа к файлу-приманке хоста и Docker socket, отсутствие секрета Django в окружении, непривилегированный UID, реальные cgroup-лимиты памяти/процессов, read-only root, блокировку сети и остановку бесконечного цикла. Отсутствие Docker/образа не включает старый небезопасный запуск автоматически. Команда должна закончиться успешно на целевой машине.

SQL по-прежнему использует отдельный ограниченный SQLite-процесс, а не Django DB. Все прежние тесты SQL выполнены и на Python 3.12. Актуальный Python/SQLite и лимиты ресурсов ОС остаются обязательными.

## HTTPS и статика

`deploy/nginx.conf` — шаблон для включения в секцию http nginx. Замените домен/пути сертификатов, проверьте `nginx -t`. `DJANGO_TRUST_PROXY=1` разрешён только с локальным reverse proxy, который **перезаписывает** X-Forwarded-Proto и X-Real-IP. Приложение использует X-Real-IP для лимитов только от loopback; не доверяет произвольному X-Forwarded-For.

```bash
gunicorn -c deploy/gunicorn.conf.py byte_project.wsgi
```

Оформите запуск через сервисный менеджер под пользователем приложения, обеспечьте автозапуск и ротацию логов. TLS-redirect, secure session/CSRF cookies, X-Frame-Options, nosniff и ограничение тела запроса включены. Приватные страницы имеют no-store/private. Статика обслуживается WhiteNoise с хешированными именами и сжатием. CSP разрешает собственные скрипты и перечисленные видеоплееры; после добавления нового внешнего сервиса пересмотреть политику. Политика CSP не навязывается Django admin.

## Ежедневное обслуживание

- Согласованная резервная копия БД в закрытый каталог, контроль восстановления и свободного диска. При переносе копий — шифрование и подтверждённое место хранения.
- `python manage.py clear_request_buckets` удаляет истёкшие счётчики защиты. В таблице ключи HMAC, а не открытые IP/логины.
- Контроль 5xx/429, CPU/RAM/диска, времени ответа и ошибок Docker. Периодически обновлять Python, зависимости и образ judge; после обновлений повторять аудит и интеграционные проверки.
- AI в примере production отключён. Перед включением проверить настройки Gemini, расходы, описание передачи данных во внешнюю систему и реальные ответы. Тайм-аут одного API-вызова ограничен, повторные попытки SDK ограничены.

## Условия первого запуска

1. Доменные имена, HTTPS, secure cookies и изоляция Docker проверены на реальном сервере.
2. Пройдены тесты, миграции, collectstatic, просмотр RU/KZ и светлой/тёмной тем.
3. Реально отправлены правильные/неправильные Python, C++ и SQL решения; проверены тайм-ауты и сохранение результата.
4. Выполнена нагрузочная проверка под запланированное число учеников; зафиксированы задержки, ошибки, очередь запросов и расход ресурсов.
5. Проверены приём заявки с согласием, вход/выход, права двух учеников, восстановление копии и отсутствие публичного доступа к `.env`, БД и резервным копиям.
6. После этого — небольшой пилот с известными участниками, затем расширение доступа.
